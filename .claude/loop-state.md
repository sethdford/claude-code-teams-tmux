## Approach: normalize-then-group, not similarity scoring

The `pattern-matching-similarity-scoring` skill suggests Levenshtein/Jaccard pair scoring. I **rejected** that: it's O(N²) in bash over hundreds of issues (this repo just merged a fix for exactly that — the O(N²) dead-code scan), and a tunable similarity threshold can silently start closing legitimately distinct issues. Instead: normalize each title to a canonical key (strip `[automated]`, `#3502`, timestamps, SHAs, all digits, punctuation), concatenate with the sorted label set, and `sort | uniq` — O(N log N), one `jq`/`awk` pass, and structurally incapable of clustering two genuinely different titles.

## Key design points

- **Top-level function, not nested.** All nine existing patrol checks are nested inside `daemon_patrol` — which makes them unreachable from `sw-lib-daemon-patrol-test.sh`, which sources the lib and calls functions directly. The acceptance criteria demand unit tests, so `patrol_duplicate_issues` / `patrol_group_duplicate_issues` / `_patrol_normalize_title` go top-level, returning findings via a `PATROL_DUP_FINDINGS` global rather than closure capture.
- **Three safety gates** against the central risk (closing real work): the group must carry an automation label (so unlabelled human issues can never be touched), assigned issues are excluded, and issues in the daemon's `.active` state map are excluded.
- **Closure cap** (`max_closures`, default 25/run). A runaway generator emitting 400 dupes would otherwise get us rate-limited mid-patrol.
- **Both config key forms accepted.** The issue names `patrol.duplicate_issue_threshold` (flat); the house convention is `patrol.checks.<name>.threshold` (nested). The loader reads flat-first, falling back to nested, so the literal acceptance criterion passes without breaking style.

## Two things worth flagging

1. **Semantics of "> 3":** I read "when >3 near-duplicates are found" literally — a group of exactly 3 is a no-op, 4 triggers. There's a test pinning the equality boundary either way.
2. **This is a safety net, not the fix.** Whatever emitted #3502–#3523 is still running. The patrol cleans up after it; source-side rate limiting is a separate issue worth filing.

E2E tests are explicitly scoped out with reason — the only true E2E would mutate real GitHub issue state, and the repo's E2E suites run without API keys by design. Coverage is 16 unit + 6 integration tests against a recording `gh` mock.

## Testing Strategy Expertise

Apply these testing patterns:

### Test Pyramid
- **Unit tests** (70%): Test individual functions/methods in isolation
- **Integration tests** (20%): Test component interactions and boundaries
- **E2E tests** (10%): Test critical user flows end-to-end

### What to Test
- Happy path: the expected successful flow
- Error cases: what happens when things go wrong?
- Edge cases: empty inputs, maximum values, concurrent access
- Boundary conditions: off-by-one, empty collections, null/undefined

### Test Quality
- Each test should verify ONE behavior
- Test names should describe the expected behavior, not the implementation
- Tests should be independent — no shared mutable state between tests
- Tests should be deterministic — same result every run

### Coverage Strategy
- Aim for meaningful coverage, not 100% line coverage
- Focus coverage on business logic and error handling
- Don't test framework code or simple getters/setters
- Cover the branches, not just the lines

### Mocking Guidelines
- Mock external dependencies (APIs, databases, file system)
- Don't mock the code under test
- Use realistic test data — edge cases reveal bugs
- Verify mock interactions when the side effect IS the behavior

### Regression Testing
- Write a failing test FIRST that reproduces the bug
- Then fix the bug and verify the test passes
- Keep regression tests — they prevent the bug from recurring
