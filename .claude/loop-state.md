# Implementation Plan: Pipeline State Corruption Auto-Recovery with Atomic Writes

## Summary

The pipeline's authoritative runtime state lives in `.claude/pipeline-state.md` (YAML frontmatter + Markdown log), written by `write_state()` in `scripts/lib/pipeline-state.sh` and read back by `resume_state()`. Today `write_state()` performs a **non-atomic two-step write** (`cat > "$STATE_FILE"` to emit the opening `---`, then a `{ ... } >> "$STATE_FILE"` block). A crash, full disk, or concurrent run between those steps leaves a truncated/interleaved file. `resume_state()` then parses it line-by-line with **no validation** and bails with `exit 1` ("Could not parse goal") — the mysterious "pipeline won't start" failure.

This plan makes every state write atomic, validates state on load, and rolls back to a last-known-good copy or the last checkpoint when corruption is detected. We **reuse existing infrastructure** (`atomic_write`, `validate_json`, `check_disk_space`, the `flock` pattern in `helpers.sh`; checkpoint JSON via `sw-checkpoint.sh`) rather than building new primitives.

> **Note on "JSON" in the issue:** the canonical state file (`pipeline-state.md`) is YAML-frontmatter Markdown, not JSON. "Validate JSON schema" is therefore implemented as **structural frontmatter validation** (delimiters + required keys). The JSON sidecar artifacts (checkpoints, `recovery-state.json`) already round-trip through `jq` and gain a shared atomic writer.

---

## Alternatives Considered

1. **Convert `pipeline-state.md` to a pure `.json` file with a JSON Schema validator.** — *Rejected.* Blast radius is huge: `resume_state()`, the dashboard (`dashboard/server.ts`), the `session-started.sh` hook, `sw-status.sh`, and human readers all consume the Markdown format. Trade-off: cleanest validation story, but breaks too many consumers for a P0 reliability fix. Maintainability cost outweighs the benefit.
2. **Atomic write + structural validation + checkpoint rollback, keeping the Markdown format (CHOSEN).** — Minimal blast radius (touches `pipeline-state.sh` write/load paths only), reuses `atomic_write`/`flock`/checkpoints already in the tree. Trade-off: validation is structural (required-key presence) not a full schema — sufficient for the real failure mode (truncation/interleaving), low complexity, high maintainability.
3. **flock-only serialization, no rollback.** — *Rejected.* Locking prevents concurrent interleaving but does nothing for a crash mid-write or a pre-existing corrupt file on disk; the acceptance criteria explicitly require rollback. Lowest complexity but fails the core requirement.

**Chosen:** Approach 2 — smallest blast radius, satisfies all six acceptance criteria, leans on proven helpers.
