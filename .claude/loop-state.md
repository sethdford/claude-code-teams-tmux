# Implementation Plan: Project Type Auto-Detection and Smart Template Recommendation Engine

## Brainstorming & Design Reasoning

### Requirements Clarity
**MVP**: A bash module (`scripts/lib/project-detect.sh`) exposing `detect_project_type()` that scans manifest files (package.json, Gemfile, requirements.txt, go.mod, Cargo.toml, pom.xml) and returns `{type, framework, language, package_manager, test_cmd, build_cmd, recommended_template}` as JSON. Integrated into `shipwright prep` with an `--interactive` confirmation step that writes results into `.claude/daemon-config.json`.

**Implicit requirements**:
- Must be Bash 3.2 compatible (no associative arrays)
- Must not overwrite existing daemon-config.json values without confirmation
- Detection must be deterministic and fast (<2s on typical repos)
- Must integrate with existing `sw-prep.sh` (1831 lines — large, add hook rather than rewrite)

### Design Alternatives

**Alternative A: Single-file detection library (CHOSEN)**
- New `scripts/lib/project-detect.sh` sourced by `sw-prep.sh`
- Priority-ordered manifest detection with confidence scoring
- Trade-off: simpler, reuses existing prep flow / less modular than per-type files
- Blast radius: minimal (one new lib + small hook in sw-prep.sh)

### Test Pyramid
- **Unit tests** (70%): Test individual functions/methods in isolation
- **Integration tests** (20%): Test component interactions and boundaries
- **E2E tests** (10%): Test critical user flows end-to-end

### What to Test
- Happy path: the expected successful flow
- Error cases: what happens when things go wrong?
- Edge cases: empty inputs, maximum values, concurrent access
- Boundary conditions: off-by-one, empty collections, null/undefined

### Test Quality
- Each test should verify ONE behavior
- Test names should describe the expected behavior, not the implementation
- Tests should be independent — no shared mutable state between tests
- Tests should be deterministic — same result every run

### Coverage Strategy
- Aim for meaningful coverage, not 100% line coverage
- Focus coverage on business logic and error handling
- Don't test framework code or simple getters/setters
- Cover the branches, not just the lines

### Mocking Guidelines
- Mock external dependencies (APIs, databases, file system)
- Don't mock the code under test
- Use realistic test data — edge cases reveal bugs
- Verify mock interactions when the side effect IS the behavior

### Regression Testing
- Write a failing test FIRST that reproduces the bug
- Then fix the bug and verify the test passes
- Keep regression tests — they prevent the bug from recurring
