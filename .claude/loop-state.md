# Implementation Plan: Intelligence Feature Impact Analyzer with A/B Test Framework

**Issue:** #661 · **Priority:** P2 · **Complexity:** standard · **Branch:** `feat/intelligence-feature-impact-analyzer-wit-661`

## Goal

Prove (or disprove) that intelligence features (predictive scoring, adaptive timeouts, model routing, convergence detection, adversarial review, etc.) actually improve success rate and/or reduce cost. Build an analyzer that performs controlled A/B comparison of pipeline runs with intelligence **enabled vs disabled**, scores per-feature ROI, generates a monthly report, auto-disables negative-ROI features in `daemon-config.json` (with explanation), and is reachable via `shipwright intelligence impact`.

---

## Design Decision & Alternatives Considered

The acceptance criteria say "runs identical issues twice." Taken literally that means actively launching ≥40 full pipelines (20 pairs). Each pipeline costs ~$2.50 and takes minutes-to-hours, and the same issue rarely produces identical outcomes twice. Mandating 40 live runs as the *only* path is cost-prohibitive, flaky, and non-deterministic. I evaluated two approaches:

**Approach A — Live-only A/B harness (rejected as default).** A command that loops over issues, runs each pipeline twice (intel on/off) back-to-back, records the delta.
- *Pros:* Truest controlled experiment; matches the literal wording.
- *Cons:* ~$100+ and hours per report; non-determinism means even paired runs differ for reasons unrelated to intelligence; huge blast radius (spawns real pipelines); impossible to unit-test without burning budget; reaching n=20 is slow.

**Approach B — Retrospective analysis of already-tagged runs + optional active harness (CHOSEN).** The codebase **already** samples intelligence variation via `intelligence.ab_test_ratio` (0.2) in `lib/pipeline-execution.sh` and `sw-self-optimize.sh::optimize_should_ab_test()`. Every pipeline already emits run records to `~/.shipwright/events.jsonl` and cost to `~/.shipwright/costs.json`. The analyzer's primary job is to **read accumulated run records**, partition them into `intel_on`/`intel_off` cohorts (and per-feature cohorts), compute statistics, and report ROI. An **optional** `run-pair` subcommand actively executes a paired experiment on demand.
- *Pros:* Near-zero marginal cost (reads existing data); statistically honest (n accumulates for free as the daemon runs); fully unit-testable with synthetic fixtures; minimal blast radius (read-only by default; the one write — config auto-disable — is gated and explained). `run-pair` still satisfies the literal "run twice" criterion.
